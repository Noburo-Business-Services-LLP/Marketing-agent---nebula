## 2. Calendar cover not loading

Root cause. Covers were never generated for any month before today because the prompt `calendar.cover` was missing from `backend/services/promptRegistry.js`, so `buildPrompt` threw "Unknown prompt" at `contentCalendarService.js:617`, caught at line 660 and recorded as `coverStatus: 'failed'` with no `coverImageUrl`. The prompt was restored in `dbeff2c` (2026-10-18; entry at `promptRegistry.js:135`, test `backend/tests/promptIdsExist.test.js`), but a month already saved as `failed` is not retried: the calendar is only auto-covered when generated (`contentCalendarService.js:733`), so this month still has no cover until someone presses the button.

Evidence and behaviour.
- History: prompt first used in d0df755 (2026-09-04); registry entry lost in 6a53ee3 (2026-09-04, "Replace the single-post, carousel and campaign prompts"); restored in dbeff2c. The note in the earlier handover is therefore correct, and is fixed in code but not in old data.
- The page: `/content-calendar` -> `CalendarHome.tsx` Plan tab -> `ContentCalendar.tsx`. The banner (`ContentCalendar.tsx:650-698`) shows a gradient when there is no `coverImageUrl` (no broken image), a "Making the cover..." spinner for `pending`, and a "Make a cover" / "New cover" button that calls `POST /api/content-calendar/cover` (`routes/contentCalendar.js:100-121`, `api.ts:4285`). That route accepts `failed` or `none` months and any old record; it only refuses while `pending`. A stuck `pending` (server restarted mid-render) shows the spinner forever and the route will not restart it (line 107): a second possible cause.
- Generation: one LLM text call plus one 16:9 image through `generateCampaignImageNanoBanana` (`geminiAI.js:4525`), which tries OpenAI image first (`IMAGE_PROVIDER_FIRST` default openai, line 4818), Nano Banana Pro (`nano-banana-pro-preview`) as fallback, and uploads to Cloudinary. If the Cloudinary upload fails the function returns base64 (`openaiImage.js:170`); the cover code keeps only `http` URLs, so it marks `failed` (`contentCalendarService.js:651-662`). A hosted URL that later dies would show a broken banner, since the `<img>` has no `onError`.
- Cost and charging: no `apiCosts` action exists for calendar covers and no `deductCredits` call, so it is not charged to the customer; the company pays about 1 LLM call plus one picture (on the current path roughly $0.01-0.05 at gpt-image-2 low/medium incl. proofreading, `apiCosts.js:108,190-195`; $0.134 if it falls to Nano Banana Pro). Repeated "New cover" clicks are unbounded.
- Not verified: I did not touch the database or the key settings, so I cannot confirm the actual status of the owner's month; check it with `coverStatus` on that ContentCalendar document (read-only script against nebulaa_dev only).

Smallest correct fix.
1. For this month: no code, press "Make a cover" (works on a `failed` record). Needs the dbeff2c code running (restart backend).
2. Code, small: in `routes/contentCalendar.js` `/cover`, treat `pending` older than about 10 minutes as stale (needs `coverRequestedAt` on the model or use `updatedAt`), and in `getCurrentCalendar`/load, auto-queue one cover for a `failed` or `none` calendar that has items (once per day), so old months heal without a click.
3. `ContentCalendar.tsx:653`: add `onError` to fall back to the gradient.
4. Tests: `generateCalendarCover` with stubbed `buildPrompt`, `llmRouter` and image function: ready path, empty prompt -> failed, base64 result -> failed, thrown error -> failed; route test that `failed` restarts, fresh `pending` does not, stale `pending` does; the existing `promptIdsExist` test already guards the original bug.
Risks: auto-retry spends company money on every failed month if the image provider is down; cap it (one retry per calendar per day). Do not run the whole suite concurrently with the video-finishing work.

Owner decides. (a) Should covers stay free to the customer (current) or cost a small Quark amount? (b) Auto-retry old failed covers, or button only? (c) Is a calendar with no cover acceptable (gradient) rather than a stock image?

## 3. Now built (2026-10-19)
