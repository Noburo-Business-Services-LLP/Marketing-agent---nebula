# Stage 4 real-database check (after fix rounds A and B), 2026-10-17

Script: `backend/scripts/competitors-realdb-check.js` (`node scripts/competitors-realdb-check.js`, or `cleanup` to remove leftovers of an interrupted run). It refuses any database except `nebulaa_dev`, prints PASS/FAIL per check, and deletes everything it made in a `finally`.

## Safety
- No real scraper, search or AI call. `socialMediaAPI.scrapeInstagramProfile` and `searchInstagramByName` are replaced by a fake BEFORE any route is loaded; every call is counted and a trip-wire check fails the run if any handle other than a throwaway `zz.rdbchk.*` handle was read (result: 24 to 25 fake reads, 0 unexpected).
- Spend guard is a fake (the shared daily spend counter was never touched). The lease uses its own OpsState keys (`competitor_tracker_lease_rdbcheck4-*`), never the real key `competitor_tracker_lease`, so a running tracker is not blocked. The real lease row does not exist in the dev database (no tracker has ever run there).
- Ports 3000 and 5000 were listening (the owner's servers); not touched. The checks used an in-process Express server on a random 127.0.0.1 port mounting the real `routes/staff`, `routes/competitorInsights` and `routes/competitors`. For the staff route only the tracker runner is injected (fake scraper, fake spend, test lease), so the staff route, `requireStaff`, the cap logic and the audit write are the real ones.

## Results (final run: 35 PASS, 0 FAIL)
1. Lease: first claimant gets it; two simultaneous claims (8 rounds, plus three claimants through the lease object) give exactly one winner and the store never throws (the E11000 path returns "not claimed"); two simultaneous claims on an expired lease give exactly one winner; an expired lease can be taken; renew moves the stored value, a stale renew changes nothing; release empties it and it can be claimed again.
2. Read log: after `Model.init()` the indexes are `at_1` (TTL, expireAfterSeconds 1209600 = 14 days), `day_1_userId_1`, `competitorId_1_at_-1`, `userId_1`. One row per attempt (tracker, staff, customer sources; a fresh ledger with no memory counts them from the database). With the snapshot save AND the tracking save failing, the read still leaves its read-log row, no snapshot exists, and the next pass (fresh ledger instance) reads nothing.
3. Paged account query, page size 3: 11 matching accounts came back over 4 pages with no repeats and no gaps; free, inactive, not-onboarded, staff and CSM accounts and a free-tier workspace are left out by the query. A full pass with `ACCOUNTS_PAGE: 3` read the 7 entitled accounts plus the active agency workspace in the exact order: never-read accounts (by id), then oldest read first. Not read: the account without the add-on, and the frozen workspace (blocked by the REAL `backgroundGate` against the dev database). Every read account got `competitorsReadAt`.
   - Wording note: "hidden agency-client accounts excluded as designed": the design (final review, spec) is that a hidden workspace of an ACTIVE agency plan is entitled and IS tracked; frozen workspaces, workspaces of an ended plan (tier free) and workspaces of an agency waiting for deletion are excluded. That is what was checked, and it behaved that way.
4. `User.updateOne(..., { timestamps: false })` sets `competitorsReadAt` and leaves `updatedAt` unchanged (a control update without the option does move it); a whole tracker pass also leaves `updatedAt` alone.
5. Tracker pass with a fake scraper: first pass saved two snapshots (all fields, including `topPost.type`, stored), the suggested handle was not read; a second pass 13 hours later read nothing; after the handle was confirmed it was read. The daily ceiling (set to today's count + 2) stopped after exactly 2 reads while every snapshot save failed (0 rows, 2 read-log rows): it counts reads, not rows. The per-account cap (1) stopped account R after one read and the pass went on to the next account. A pass releases its lease; a pass whose lease is held elsewhere reports `busy` and reads nothing.
6. Routes with real login tokens: PUT handle 200 (leading @ stripped, `handleStatus` confirmed, pause, failures and last check cleared), 400 for five bad inputs, 404 for another account's competitor (untouched) and for a malformed id, 401 without a token, 403 with the standard upgrade body without the add-on (also for GET insights), 429 on the 31st call (30 allowed) while another account was unaffected. Insights return `handleStatus`, `weekOf`, `isCurrentWeek`, `previousWeekOf`, `lastCheckedOn`; a competitor with only an older snapshot is not current, has `lastCheckedOn` and no highlight; a snapshot row filed under A's competitor but owned by B (planted) was ignored; none of B's names, ids, handles or numbers appear in A's response and vice versa. Staff `POST .../competitors/check`: 403 for a customer token, 404 for an unknown client; with force it read a competitor already checked this week exactly once (a normal pass would not), wrote one `check_competitors` audit row (actor = staff, details.checked 1) and one `staff` read-log row; a second call with a per-account cap of 2 read nothing and was still audited. Staff GET shows the client's view only.
7. Deletion: `removeCompetitorsWithSnapshots` removes the competitor and its snapshots and no one else's; the real account-deletion `data` step (registry path, `stepsFor`) removed the throwaway account's competitors, snapshots and read-log rows (7 records over 50 collections) and left another account's rows.

## Defects and fixes
No defect in the Stage 4 code was found by the real run. Two script mistakes of mine were fixed along the way (a lease I claimed and did not release, and a slow stray scan), and one run had a single check fail on a network DNS error to Atlas (not a defect; the rerun was clean).
One small seam added so the paging can be tested for real: `tracker.defaultDeps().accounts` takes an optional `pageSize` (the pass passes `caps.ACCOUNTS_PAGE`, which is not set in `config/competitors.js`, so production still uses 500) and `defaultDeps` is exported. Unit test added first in `tests/competitorTracker.test.js` ("(I11) the account lookup is asked for pages of caps.ACCOUNTS_PAGE ...").
