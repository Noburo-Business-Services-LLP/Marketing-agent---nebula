# Stage 2 final whole-branch review (684c764..af65cd0)

Reviewer: final review, read-only. Pure unit tests run: backend week/setup/planContext 67/67 pass, frontend week/setup/prefill 17/17 pass.

## Verdict

No Critical defect found in the Stage 2 code. The money core of the weekly flow holds up against the final routes: claims are atomic, a post is charged once, a lost runner writes and refunds nothing, refunds go back to the wallet that paid, and spendGuard is checked before each charge. Page loads cannot start an automatic retry loop of a failing post. A failed post is only tried again when someone presses "Try again", and the only automatic retry is the 10-minute takeover of a crashed post, which charges nothing.

Three Important items should be decided before launch:
- **I1:** the plan fallback can propose, charge for and make a second week of posts when the calendar week is already made.
- **I2:** carousels and videos never become "made", so the card keeps offering "Make this video" and each Generate press charges again.
- **I3:** the calendar auto-generation cost leak. It is older than Stage 2, it is confirmed and worse than first thought, and the weekly flow does not protect against it, contrary to a code comment.

## Important

### I1. The plan fallback starts when the calendar week is already made or rejected, not only when there is no calendar (confidence: high)
`backend/services/week/weekService.js:39-55` (calendarItemsForWeek drops rows that have `generatedDraftId` or a status in `DONE_STATUSES`) and `:194-196` (getOrCreate uses `planCalendar` whenever `calendarItems` is empty).

Failing scenario: a paying customer presses "Generate this week" on the Calendar page (`POST /api/content-calendar/:id/auto-generate-week`, free). Or auto-generation has made the days. Or the customer rejected every row of the week. They then open Home for the first time that week. `calendarItemsForWeek` returns `[]`, so the proposal is built from the plan's 30-day calendar. That is about 7 new items with `source: 'plan'`, and each one is made from a one-off in-memory calendar that never checks the real rows. Approve then charges and makes about 5 new posts for a week that already has its posts, or whose ideas were rejected. The card says "based on your plan", so nothing tells the customer they are paying for a duplicate week.

The spec allows the plan fallback only for "No calendar yet". Fix: use the plan only when the account has no calendar rows at all for those days, counted before the done or rejected filter. When rows exist but none is open, return the "Nothing left to make this week" state.

### I2. Carousels and videos never reach "made", so the card keeps asking to make them again (confidence: high)
`weekService.js:319` (a non-post item goes to `approved` and stays there), `frontend/utils/week.ts:43-47` (`partly` while any non-post is `approved`), and `frontend/components/ThisWeekCard.tsx:157` (`canMake = item.kind !== 'post' && item.status === 'approved'`).

Failing scenario: the customer approves, presses "Make this video", generates it on /reels and pays the video price. Back on Home the card still shows "Make this video" for the rest of the week, and pressing it pre-fills the screen again. A second Generate charges the full video price again. Nothing records the video against the item.

The spec says: "Nothing is made twice … 'made' is set from the real created draft or job id". That rule is met for single posts only. Fix: pass the `itemId` through the prefill and mark the item made with the job or draft id when Generate succeeds. A cheaper alternative is to mark the item `opened` the first time it is handed over and change the button to "Open again".

### I3. Calendar auto-generation cost leak (older than Stage 2; confirmed, larger than flagged) (confidence: high on the mechanism, medium on the multiplier)
`backend/services/contentCalendarService.js:822-864`, `:866-877`; `backend/routes/contentCalendar.js:121-153` (settings), `:73-84` (regenerate), `:361-386` (auto-generate-week).

- `processAutoGeneration` skips only `rejected|published|scheduled` (`:840`). A row marked `generated` is made again on every tick (once a minute) until `autoGeneratedCount` reaches `autoGenerateLimit`. The default is 7, and the customer can set anything from 1 to 31. Every post is the same day's row, and each one overwrites `generatedDraftId`, so the customer finds several duplicates in Review and approve.
- `setInterval` does not guard against overlap. One generation takes about 150 s and the interval is 60 s, so 2 to 3 ticks generate the same calendar at once. Each saves `count+1` from its own stale read, so updates are lost. Estimate: about 2.5 times the cap in posts (default about 17 posts, at limit 31 about 75).
- Switching auto-generation off and on resets the count to 0 (`routes/contentCalendar.js:135`). There is no rate limit, so this is unbounded, at about 1 post a minute while the cycle repeats.
- `todaySuggestion` (`:746-750`) uses today's date in any calendar that has auto on and approved. A next-month calendar with auto on also makes "today's" row now. It also falls back to `items[0]`.
- `auto-generate-week` (free, no rate limit) makes every open row of a week. `regenerate` (free, no rate limit) replaces the month's rows with new ones, which auto-generate-week can then make again, so the loop is unbounded.
- None of these paths call `spendGuard.check`, and none record spend: `record` is only reached through `deductCredits` and quarkBuckets. **The daily AI ceiling and the provider kill switches do not stop this spend, and it does not count toward the ceiling.**

Realistic exposure per account per month, at about Rs 1 to 4 a post:
| Path | Posts | Cost |
|---|---|---|
| Default auto cap | about 7 to 17 | about Rs 7 to 70 |
| Auto limit set to 31 | about 31 to 75 | about Rs 31 to 300 |
| Monthly auto-generate-week | all open rows, about 30 to 60 | about Rs 30 to 240 |
| Toggle or regenerate abuse | unbounded | about Rs 60 to 240 an hour for one account |

Did Stage 2 make it worse? Barely. The plan guidance adds up to 900 characters to the monthly calendar prompt. That is one text call per calendar generation, a few paise. But two interactions matter:
- `weekService.js:122-123` claims the saved row "so the monthly auto-generation does not make the same day again". That is false, because auto-generation ignores `generated`. A weekly post the customer paid for, made for today's row on an auto-on calendar, is made again for free (duplicate draft, cost to us). The reverse direction is safe: a row auto-generation already made is adopted by `makePost` without a charge (`:250-254`), and it is excluded from new proposals.
- The two flows can race. If a weekly post is `making` for today's row, the row is not marked until generation ends, so the auto tick generates the same row at the same time (two model runs, one charge).
- `regenerate` replaces the row ids. Weekly items that point at the old rows then fail with `no_calendar` before any charge, and the card shows "Could not be made, try again" for the rest of the week. Every retry fails the same way.

Recommended fixes, decided by the owner: skip `generated` and `generatedDraftId` rows in `processAutoGeneration`, add a reentrancy guard on the scheduler, stop resetting the count on toggle (or keep a monthly counter per account), add `spendGuard.check` and `record` around `generateSingleCalendarItem` callers, and rate-limit or charge regenerate and auto-generate-week.

## Minor

- **M1. Posts are made in parallel, not "one at a time".** `routes/week.js:61` and `ThisWeekCard.tsx:50-55`. Every 5 s poll calls GET, which fires `runApprovedPosts`. While item 1 is generating, the next poll claims item 2, and so on. There is still no double charge (claims are atomic), but one account can drive N image generations at once, and the comment at `weekService.js:326` is wrong. Each such GET also runs `blockedAccountIds()`: three global `User` queries, plus a fourth when agency owners exist, on every poll while posts are open. Prefer a per-user status check and an in-process "already running for this user" guard.
- **M2. A closed spend guard looks like endless "Making…".** `weekService.js:257-261` puts the post back to `approved`. The card shows "Making…" and polls every 5 s for as long as the guard stays closed (up to a day), and every poll claims, checks and releases. There is no customer message such as "busy, we will make these later".
- **M3. GET /api/week returns 500 when the gate read fails.** `routes/week.js:61`: `await blocked(userId)` throws inside `handle`, so the whole read fails with 500. The Task 5 report says it "skips the background run on GET". The card then shows its load error.
- **M4. `firstWeekApprovedAt` is stamped inside a CSM or agency pass.** `weekService.js:322`; the route does not exclude passes, unlike `planOpenedAt` (`routes/plan.js:107`). That is defensible for managed clients (the CSM approved the week), but it does not match the stamping rule used for the plan step.
- **M5. No retry cap.** Each "Try again" (`ThisWeekCard.tsx:154`) re-runs the text and image models for a post whose generation keeps failing, for example when the image model refuses a swapped topic. The customer is refunded each time; the model cost is ours. This is bounded only by the write limit (30 per 15 min per account). A `no_pool` failure also shows "Could not be made, try again" instead of pointing to top-up.
- **M6. A failed refund can end in a double refund or a free post.** The alert at `weekService.js:227` asks the owner to refund by hand, while the item keeps `charged: true`. If the customer later presses Try again and generation fails again, `refundOwned` refunds automatically, which is a double refund if the owner already refunded. If generation succeeds after a manual refund, the post was free.
- **M7. A post stuck after a crash can stay charged.** Recovery happens only on page loads, for 14 days. A server restart in the middle of a post leaves it `making` with `charged: true` until someone opens Home. There is no server sweeper and no cap on takeover attempts.
- **M8. Kill switch.** `ENABLE_WEEKLY_PROPOSAL=off` stops new runs and writes, but not a `runApprovedPosts` loop already running (it keeps making the remaining posts). Posts already approved resume and are charged when the switch is turned back on, up to 14 days later.
- **M9. Agency workspaces.** Each client workspace's proposal is scaled against the whole shared agency pool on its own, so several clients' proposals together can exceed the pool. Their posts then fail as `no_pool`, shown as "try again". The wording does not say the balance is shared.
- **M10. Plan-sourced items.** An empty `hook.text` gives a blank topic (`weekProposal.js:16`). The spec says to use generic topics from the pillars. `calendarFor` derives the row day from the proposal index instead of the plan day (`weekService.js:148-149`; cosmetic, `calendarDay` only). The plan-sourced post path (in-memory calendar) was not part of the real run.
- **M11. Month-end week.** `calendarItemsForWeek` correctly reads both months' calendars. If the next month's calendar does not exist yet, those days are simply missing (the plan does not fill them), so the week is shorter.
- **M12. Accessibility.** After "Skip" on an item the focused button is removed and focus drops to the page body. "Change" opens the input without moving focus into it.
- **M13. Prefill language source.** The prefill language falls back to `businessProfile.contentLanguage` on the frontend (`GravityHome.tsx`) but `businessProfile.language` on the backend (`weekService.js:168`), so a reload after approve can pre-fill a different language.

## Checked and fine

- **Cost safety:**
  - Approve only claims. A double press, two tabs, or approve followed by skip change nothing: skip works only on `proposed`, and skipWeek only on a `proposed` week.
  - A change in the pool between proposal and approve cannot overdraw it, because each post is an atomic `quarkBuckets.spend`. A refused charge fails as `no_pool`, with no model call.
  - `charged` and the `makingAt` token rules were re-checked against the final routes. A failed post is never retried automatically by GET (only `approved` posts and `making` posts older than 10 minutes are picked up).
  - spendGuard is checked before each charge, and spend is recorded through deduct. Carousels and videos are never made automatically.
- **Access:**
  - All routes use `protect` plus per-user limiters. The account key is always `req.user._id`, so there are no reads across accounts.
  - Staff are refused on writes and are not eligible for GET (`shouldHavePlan`). A CSM pass is allowed, as the owner decided.
  - An agency pass uses the workspace as `req.user`: the pool is read through `walletBalance` (the agency's pool, or 0 when frozen) and charged through `resolvePayer`, and the refund goes back to `chargedTo`.
  - The background gate applies on approve and on the GET run. `planOpenedAt` is not stamped by CSM, agency or staff sessions.
- **Data:**
  - `WeeklyProposal` is in `dataRegistry` with delete. There is a unique index on `userId+weekStart`, autoIndex is on by default, and the duplicate-key re-read works.
  - `User.setup` in the public JSON holds two dates only. Weeks start on Monday in Asia/Kolkata.
- **Frontend:**
  - States are mapped. Polling is a self-rescheduling timeout that is cleared on unmount.
  - The prefill is read once and removed (sessionStorage, 15-minute expiry).
  - The Setup card is hidden for staff, CSM passes and agency workspaces. The This week card is hidden for staff themselves.
  - No Quark, vendor or "credit" words in the customer text (the top-up link route is `/trial-expired`, which appears only in the URL).
  - If the week API fails on first load, a role="alert" message is shown; later failures show the error but keep the last data.
- **Calendar guidance:**
  - The prompt is byte-identical without a plan (`[focus, ''].filter(Boolean)`), and `planGuidanceFor` never throws.
  - The guidance text comes from the plan run's output, clipped to 900 characters, and goes into the prompt's input section, not the JSON template, so it cannot break the parse. The customer could already steer this prompt more directly through their focus, ideas and profile fields, so it adds no new injection surface beyond their own calendar.
  - A swapped topic (200 characters at most) reaches the post generator just as a Create brief does.
