- **D25 (2026-10-20, load-test week 1)** Passwords and sign-in codes are hashed with the native `bcrypt` package (6.0.0, prebuilt binary for linux x64 glibc, verified loading on `node:20-bookworm-slim` amd64, the release base image, with no build tools) through one helper `backend/services/passwordHash.js`: work on the libuv thread pool, at most 3 at once, a bounded queue (100) and a plain 503 "Please try again in a moment." when full. Cost factor: `BCRYPT_ROUNDS`, default **11** (was 12 with bcryptjs; OTP codes stay at 10). Why 11: one hash costs roughly half of cost 12, which is what lets one instance serve 10 to 25 sign-ins a second; 11 is inside normal guidance for bcrypt (OWASP's floor is 10) and accounts are also protected by the 5-attempt lock and the per-account sign-in limit. Security note: the owner can raise it at any time by setting `BCRYPT_ROUNDS=12` (or higher) in the task environment; existing hashes keep working at any cost, and a password stored at another cost than the setting is stored again at the setting after its next successful sign-in. Reverse: set `BCRYPT_ROUNDS=12`; to go back to bcryptjs, revert the commit (old and new hashes are the same format, so nothing in the database needs changing).
- **D26 (2026-10-20, load-test week 1)** Auth: a short in-process cache for the HOT READ routes only, not a lean `req.user` everywhere. The audit (`docs/superpowers/ops/auth-cache-audit.md`) found about 150 places in 23 route files that hand the whole `req.user` to services, several reading nested money and plan fields, so a default-lean `protect` would need a line-by-line rewrite with a large blast radius on plan gating and money. DECISION: `protect` stays exactly as it was (full, fresh document) for every money, plan, entitlement and write route; a new `protectCached` (same checks and answers, lean projected frozen user with `id` and `_id`, 15 s per token context including the CSM/agency pass, LRU 5,000) is used only on `GET /api/auth/me`, `/api/credits`, `/api/credits/history`, `/api/notifications`, `/api/notifications/unread-count` and `/api/home/summary` (which builds from a fresh document on its own cache miss). Every write to a User clears that user's entries through schema hooks (save, every update/delete query, bulkWrite, insertMany), before and after the write. Known limit, accepted: with two or more server processes a write in one process is seen by the others after at most 15 s, and only on those read routes (every write and money route refuses at once); there is no token version, so a password change does not revoke old tokens (it never did). Measured on the dev database: `/me` p90 at 50 TPS 1426 ms to 117 ms, max 62 to 123 TPS; unread count p90 210 to 93 ms, 63 to 122 TPS; credits p90 968 to 317 ms. Reverse: `AUTH_CACHE=off` (instant fallback to `protect`), or revert the commits. Details: `docs/superpowers/ops/auth-cache.md`.
